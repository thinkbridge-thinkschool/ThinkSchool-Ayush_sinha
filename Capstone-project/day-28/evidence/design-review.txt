--- Finding traced through the code ---

1. WorkOrderService.CreateAsync/AssignTechnicianAsync/StartAsync/CompleteAsync
   all call DispatchAndClearAsync, which does:
       await _dispatcher.DispatchAsync(workOrder.DomainEvents, cancellationToken);
   synchronously, in the same call stack as the HTTP request.

2. InProcessDomainEventDispatcher.DispatchAsync resolves every
   IDomainEventHandler<T> for the event type and awaits each one in a
   plain foreach loop — no try/catch around the per-handler invoke.

3. If WorkOrderCompletedHandler.HandleAsync (Assets) or
   WorkOrderCreatedNotificationHandler.HandleAsync (Notifications)
   throws for any reason, that exception is not caught anywhere between
   the handler and the ASP.NET Core pipeline. It propagates up through
   WorkOrderService, out of the minimal API endpoint delegate
   (WorkOrderEndpoints.cs), and is caught only by the top-level
   GlobalExceptionHandler, which returns a generic 500 ProblemDetails.

4. For WorkOrderService.CreateAsync specifically: the WorkOrder is
   already persisted via IWorkOrderRepository.AddAsync BEFORE dispatch
   runs. So a handler failure on the Notifications/Assets side turns
   into a 500 response for a write that already succeeded on the
   Maintenance side. There is no idempotency key on POST /work-orders,
   so a caller that retries after seeing that 500 risks creating a
   duplicate work order for the same asset.

This is the concrete, code-grounded version of the "synchronous
dependency may create availability coupling" critique category — it
directly challenges this ADR's chosen mechanism (in-process, synchronous,
inline-awaited dispatch), not a tangential concern.
